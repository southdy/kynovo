# Throughput / tail-latency curve for the two flush knobs, and the substrate control -- 2026-09-19
#
# Run on the VMware guest (CentOS 7.9, gcc 4.8.5, 4 vCPU) and on the Windows host.  Shape: bench_rate,
# N=2000 in flight, 1 B values, disk://, one client, one connection, unique keys.  Both platforms
# measured with the SAME binary shape; the knobs are set at `init` time (--flush-items / --flush-window-ms).
#
# == Substrate control: tools/harness/wake_probe (runtime task/result seam, one worker, NO storage) ==
# VM    empty  : handoff p50=29us p99=124us max=412us | wake p50=29us p99=119us | round p50=58us
# VM    busy200: handoff p50=230us p99=406us max=2427us | wake p50=59us | round p50=290us
# VM    busy5k : handoff p50=5033us max=6253us          | wake p50=113us | round p50=5153us
# Win   empty  : handoff p50=3us p99=40us max=169us     | wake p50=3us | round p50=10us
# Win   busy200: handoff p50=210us p99=274us max=398us  | wake p50=28us | round p50=242us
# => The guest's thread substrate is healthy (tens of microseconds, p99 ~0.12 ms), so the engine's
#    handoff (up to 5.8 ms) and wake (up to 1.3 ms) numbers are NOT scheduling: the WAL worker is
#    simply still busy with the batches ahead of it in the pipeline.  Queueing, not the OS.
#

# Conclusion: the best flush window is a function of the measured sync cost, and the two platforms want
# opposite settings (1 ms where the sync is 0.17 ms, 3 ms where it is 1.13 ms) - which is exactly what
# the driver's adaptive window is for.  A fixed default is wrong on one of them.  flush_item_limit=32,
# the current default, is at or near the best on both, so it stays.
