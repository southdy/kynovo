# Where the Linux ceiling actually is -- profile of one open-loop run -- 2026-09-19
#
# tools/harness/rate_profile.sh, VMware guest (CentOS 7.9, 4 vCPU, fsync ~0.17 ms), disk:// unless
# noted, 1 B values, N=2000, bench_rate (one connection), window 1 ms, items 128.  ONE session, so the
# rows are comparable to each other and to nothing else.
#
# K     ops/s    requests/round   rounds/s   per batch   p50      p99
#  64   16839          5            3334        52        3358     6270
# 128   18170          5            3261        37        5405     9852
# 512   54677          8            6287        91        7833    11043
# 2000  42872          9            4480        74       11292    17070
# mem:// K=512 (sync 3 us)  45573-89944 depending on machine state, batch 29-30
#
# Read it as: throughput == rounds/s x requests-per-round (5x3334=16.7k, 8x6287=50k).  Two facts follow.
#
# 1. Storage is not the wall on this platform.  With 91 requests per batch and a 0.17 ms sync the fsync
#    ceiling is ~529k ops/s, and the engine reaches 55k - about 10% of it.  mem://, whose sync costs 3 us,
#    lands in the SAME class (45-90k) instead of two orders higher, which is what a storage-bound engine
#    would show.  So the event loop, not the disk, sets the ceiling here, and the same holds on Windows
#    (43-58k with a 1.13 ms sync).
# 2. Only 5-9 requests are admitted per round even with 2000 in flight, and a round costs ~160-300 us.
#    That pair IS the throughput.  Raising K does not raise requests/round much, so the limit is not the
#    client's willingness to have work outstanding; it is how much the loop ingests and finishes per turn.
#
# Ranked levers, all measurable next (none of them implemented yet, so this is a direction, not a claim):
#   a. per-round cost (160-300 us): decompose a round - decode, apply, encode, flush bookkeeping - and
#      look for per-request work that can be done per batch instead.
#   b. requests per round (5-9): whether the loop drains every frame already available at the socket
#      before returning, or one arm per frame keeps it shallow (cemon_recv arms ONE completion).
#   c. more CPU: the guest has 4 vCPU and the server used ~1.3 cores at 90k ops/s on mem://, so the
#      remaining vCPU is the cheapest untapped resource - noting the host itself is shared.

# ---------------------------------------------------------------- continuation: how far Linux really goes
# Same day, same box.  Everything below is disk://, 1 B values, N=3000 per client, window 1 ms,
# items 128, one server, clients as separate bench_rate processes.
#
# clients  where          ops/s (total)   what it means
#    1     in the guest      33k-55k      a single bench_rate process cannot keep the pipe full: its own
#                                        loop turn paces the server, and both share 4 vCPU
#    4     in the guest      82.5k        scaling, still sharing the box with the server
#    4     from the host    141.8k-150.2k real TCP from another machine - 2.6x the best single client
#
# Server-side reading taken during the guest-only 4-client run: rounds=239, client_requests=12018,
# frames_max=754, poll_us_ewma=2437, round_us_ewma=183, sync_us_ewma=708.
#   -> 50 requests admitted per round (against 5-13 with ONE client) and a single round that took 754.
#   -> cpu_us_per_op measured 1-6 us across the earlier sweep, so the server was never CPU-bound.
#
# Ceiling check: throughput == batch / fsync.  With the batch actually measured at 91-128 requests and a
# 0.7 ms sync, the bound is ~130k-183k ops/s, and the engine reaches 150k - i.e. once it is fed in
# parallel it sits AT the group-commit bound, not at some loop limit.
#
# So the answer to "is there headroom left on Linux" is: the single-client numbers were a BENCHMARK
# artifact, most of the apparent headroom was an under-fed server, and the remaining headroom is the
# batch/fsync term itself - larger --flush-items/--flush-bytes (fewer syncs per request) or a faster
# sync.  The loop's own work is worth 1-6 us per request and ingests up to 754 frames per round.
#
# Latency side is unchanged by any of this: the tail tracks offered concurrency (K), with p50 0.65 ms
# (mem) / 2.8 ms (disk) at K<=64 and 7.8-11 ms at K=512.

# ---------------------------------------------------------------- latency-budget knob: tested, no win
# --latency-budget-ms <N> caps how long a request may queue behind durable work: the driver sets the
# WAL in-flight depth to N/measured-sync (clamped to the compile-time cap), and STATS exposes both the
# budget and the resulting wal_inflight_max, so the policy is never invisible.  Default 0 = off, so
# nothing changes unless it is asked for.
#
# Windows, disk://, 1 B, items 128, window 1 ms, single client, K=512, THREE alternating pairs:
#   depth 4 (budget off)  64172 / 57090 ops/s   p99 12672 / 13546 us
#   depth 1 (budget 1 ms) 52907 / 58218 / 44711 ops/s   p99 14341 / 13264 / 20684 us
# The single first pair suggested depth 1 was better (52.9k vs 40.6k, p99 14341 vs 25084); the repeats
# showed the opposite twice, so that reading was machine noise.  At K=512 on this device a shallower
# durable queue does NOT buy tail latency and costs throughput: the queue is not what fills the tail
# here, and the default depth of 4 is at least as good.
# Conclusion: keep the knob off by default (it is), and do not sell it as an optimisation.  It remains
# useful as a bounded-tail setting for a device that starts syncing far slower than it used to.
#
# Incidental defect fixed while adding the flag: the server's tail-argument check was `else if(argc!=7)
# return -1;` - a SILENT refusal with no message, so a server that rejected its own arguments looked
# like a server that failed to start (it cost a debugging round).  Unknown arguments now print their
# name and the reason.
